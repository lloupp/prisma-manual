# Repository Guidelines

## Project Structure & Module Organization
This repository has two independent parts. The Next.js 16 app (App Router, TypeScript) is everything at the repo root: route files live in `app/` (`app/page.tsx`, `app/search/page.tsx`, `app/scanner/page.tsx`, `app/diagnostico/page.tsx`, and feature folders such as `app/guides/`, `app/systems/`, `app/especificacoes/`, `app/historico/`), reusable UI in `components/` by concern (`cards/`, `car/`, `layout/`, `search/`, `badges/`, `scanner/`, `diagnostico/`), static domain content in `data/`, shared helpers in `lib/` (including `lib/obd-client.ts`, `lib/agent-tools.ts`, and the pure hypothesis-based diagnostic engine in `lib/diagnostics/`), domain types in `types/`, and Prisma schema/migrations/seed in `prisma/`. Public assets belong in `public/images/`.

`obd-service/` is a **separate** Node/TypeScript package with its own `package.json`, `node_modules`, and test suite - it's the local OBD-II service described below, and never shares a dependency tree, tsconfig, or lint/test run with the root project (see the root `tsconfig.json` `exclude`, `eslint.config.mjs` `ignores`, and `vitest.config.mts` `exclude`, which all explicitly carve it out).

## OBD Scanner Architecture
The Scanner (`/scanner`) talks to a real OBD-II adapter (or a simulator) through a separate local service, never directly from the browser:

```
carro -> adaptador OBD-USB -> porta serial -> obd-service (Node, processo local)
       -> HTTP/WebSocket (localhost:4405) -> lib/obd-client.ts -> app/scanner + lib/agent-tools.ts
```

- **Why a separate service, and why Node.js**: a persistent serial connection and a long-lived WebSocket stream don't fit a request/response web server, especially one that might also be deployed to Vercel - `obd-service` is meant to run only on the user's own machine, tethered to the car. Node was chosen over Python because the rest of the codebase is already TypeScript (one toolchain, not two) and because `serialport` is a mature, actively-maintained, cross-platform package with first-class Windows COM-port support (`SerialPort.list()`), which is the explicit "Windows first" requirement for this project.
- **Transport abstraction**: `obd-service/src/transport/OBDTransport.ts` is an interface with no write/actuator/clear-DTC method - not "blocked", **absent**. Four implementations share it interchangeably (selected only via `OBD_TRANSPORT`, never known by `ConnectionManager` or the gateway): `SimulatorTransport` (12 synthetic scenarios covering normal/cold-start/warming-up/overheating/low-battery/charging-failure/lean/rich/misfire/incoherent-sensor/multiple-DTCs/limited-PIDs, plus fault-injection flags for timeout/no-response/disconnect/corrupted-response/stale-data, see `obd-service/src/simulator/scenarios.ts`), `SerialTransport` (real ELM327-over-serial), `RecordingTransport` (a decorator that transparently records every request/response of any inner transport - the RECORD step), and `ReplayTransport` (reproduces a saved recording exactly, per-request-type, marking exhausted data `stale: true` rather than repeating it silently - the REPLAY step). `SerialTransport` follows the public ELM327/SAE-J1979 protocol docs but **has not been validated against physical hardware** - this sandboxed environment has no serial port. Test it against a real adapter and car before trusting it, and update this note with the result.
- **Record/save/replay a session**: every connection is always wrapped in `RecordingTransport` (see `src/index.ts`). `GET /recording/current`, `POST /recording/save` (writes `OBD_RECORDINGS_DIR/<id>.json`), and `GET /recording/list` expose this from the gateway; `lib/obd-client.ts` mirrors them for the Next.js side. To replay a saved session, restart the service with `OBD_TRANSPORT=replay OBD_REPLAY_FILE=<path>` - the same mechanism already used to switch simulator/serial, not a separate hot-swap feature.
- **Diagnostic engine** (`lib/diagnostics/`): a deterministic, pure, rule-based engine (no LLM - none is wired up in this environment) implementing SINTOMA → DADOS → HIPÓTESES → EVIDÊNCIAS A FAVOR/CONTRA → DADOS AUSENTES → PRÓXIMO TESTE → RESULTADO → REAVALIAÇÃO. `computeConfidence` (`lib/diagnostics/scoring.ts`) structurally caps confidence at 0.65 unless a discriminating test has been reported as `confirms` for that specific hypothesis (which also adds strong evidence weight, not just a higher ceiling) - a hypothesis can never look "certain" from indirect evidence alone. Every rule in `lib/diagnostics/rules.ts` carries a `heuristicNote` distinguishing a generic OBD-II heuristic from a confirmed Prisma specification, and no rule's output ever recommends replacing a specific part - only a next test, ranked by cost/safety. `app/diagnostico/page.tsx` drives the full loop (pick scenario → connect → capture labeled samples → see hypotheses → report a guided test's result → see the hypothesis reweighted → save the session, with its hypotheses snapshot, to `DiagnosticSession`); `/historico` can reopen a saved session's hypotheses read-only.
- **Read-only enforcement** is two layers: the `OBDRequest` TypeScript union has no write variant, and `obd-service/src/validation/readOnlyGuard.ts` re-validates the same allowlist at runtime (covers untyped boundaries like an HTTP body). Mode 04 (clear DTC) is rejected even when shaped like a `READ_DTC` request. `obd-service/test/writeSafety.test.ts` and the root `tests/agent-tools-safety.test.ts` both prove, by scanning source text and runtime method names, that no write/actuator/flash/clear-DTC identifier exists anywhere in either project.
- **PID/DTC decoding** (`obd-service/src/protocol/`) only implements the universal SAE J1979 (PIDs) and SAE J2012 (DTC byte-pair format) standards - nothing Prisma-specific. `dtcDescriptions.ts` only describes the small set of codes whose meaning is standardized across all manufacturers; anything else returns `null` rather than a guessed description.
- **Running it**: `cd obd-service && npm install && npm run dev` starts the service on `http://localhost:4405` using the simulator by default (`OBD_TRANSPORT=serial` switches to real hardware; `OBD_SIMULATOR_SCENARIO` picks a simulator scenario). The Next.js app expects it there (`NEXT_PUBLIC_OBD_SERVICE_URL` overrides the URL). `/scanner` shows a clear message with the exact command to run if the service isn't reachable.
- **Agent tools** (`lib/agent-tools.ts`, 16 entries in `AGENT_TOOLS`) are the only way anything (a future LLM agent included) can read OBD data or run the diagnostic engine from the Next.js side - fixed, read-only, structured functions, never a pass-through for an arbitrary command. `capture_diagnostic_sample`/`run_diagnosis` expose the engine the same way. **This file still only defines the tool layer - there is no live LLM actually calling these tools autonomously.** The `/diagnostico` UI drives them directly from a human clicking buttons; wiring an actual tool-calling chat loop on top is still the deferred next phase, not this one.
- **History**: `DiagnosticSession` (Prisma) stores a summary per Scanner/Diagnóstico connection (DTCs, freeze frame, final live snapshot, and - only for sessions from `/diagnostico` - the labeled `diagnosticSamples`, `reportedTests`, and a `hypothesesSnapshot` of the report at save time) - not a per-second sample table, which would be overengineering for a personal tool. `prisma/seed.ts` never clears this table (it's real user history, not static manual content). `/historico` reads it and **must** stay `export const dynamic = 'force-dynamic'` - without it, Next statically prerenders the page once at build time and it never reflects new sessions (this exact bug was caught and fixed once already; see git history).
- **Not yet built** (explicitly deferred, matching the project's own phased approach): a live LLM tool-calling loop actually invoking `lib/agent-tools.ts` autonomously; broader diagnostic rule coverage (only 7 rules exist - lean/rich mixture, misfire, low charging voltage, overheating, incoherent sensor, insufficient-data - real workshop diagnosis covers far more failure modes than this proves out); trend analysis over historical sessions; replaying a saved session's raw OBD frames from the UI itself (today this requires restarting `obd-service` with `OBD_TRANSPORT=replay`, not a button in `/diagnostico`); anything GM-proprietary (ABS/airbag/BCM modules) beyond standard OBD-II; real hardware validation of `SerialTransport`.

## Build, Test, and Development Commands
- `npm run dev`: start the local Next.js dev server.
- `npm run build`: create a production build.
- `npm run start`: run the production build locally.
- `npm run lint`: run ESLint (`eslint-config-next` core-web-vitals + TypeScript rules).
- `npm run typecheck`: run TypeScript without emitting files.
- `npx prisma migrate dev`: apply local schema changes to SQLite.
- `npx tsx prisma/seed.ts`: repopulate `dev.db` from the files in `data/`.
- `npm run test`: run the content-integrity and agent-safety test suite (vitest) - root project only, `obd-service/` has its own.
- `cd obd-service && npm install && npm run dev`: start the OBD Service locally (simulator by default) - required before `/scanner` or `/historico` do anything useful.
- `cd obd-service && npm run test`: run the OBD Service's own test suite (protocol decoding, simulator fault injection, connection manager, write-safety scans).
- `cd obd-service && npx tsc --noEmit`: typecheck the OBD Service (its own tsconfig, not the root one).

Run `npm run lint && npm run typecheck && npm run test` (root) and `cd obd-service && npx tsc --noEmit && npm run test` before opening a PR. Use `.env` for `DATABASE_URL`; `lib/prisma.ts` currently defaults to `file:./dev.db` for local work.

## Coding Style & Naming Conventions
Use TypeScript and React function components. Follow the existing code style: single quotes, semicolons, and simple named exports in shared modules. Keep route components and UI components in `PascalCase` (`CategoryCard.tsx`), utilities in lowercase files (`lib/utils.ts`), and data/type files in lowercase or camelCase by domain (`data/guides.ts`, `types/repairGuide.ts`). Prefer small, focused edits over broad rewrites.

## Testing Guidelines
`tests/content-integrity.test.ts` (vitest) enforces the technical-accuracy rules for this project: every specification/part/fluid/interval/torque marked with a confidence above `UNVERIFIED` must have a matching `SourceReference`, `OFFICIAL` claims need an `OFFICIAL`-confidence reference, every `TorqueSpecification` row must cite a source (the table may simply stay empty instead), and every guide needs a non-empty `precautions` list, a valid `partId`, and sequential step numbers. Run `npm run test` before adding or changing anything in `data/parts.ts`, `data/guides.ts`, `data/specifications.ts`, `data/fluid-specifications.ts`, `data/maintenance-intervals.ts`, `data/torque-specifications.ts`, or `data/source-references.ts`. Never add a specification with `confidence` above `UNVERIFIED` without a real, checkable source in `data/sources.ts` — see the "Rastreabilidade" rules for this project.

`tests/agent-tools-safety.test.ts` enforces that `lib/agent-tools.ts` exposes exactly the expected read-only tool set and that no write/actuator/clear-DTC/flash identifier exists anywhere in the Next.js app (mirrored in `obd-service/test/writeSafety.test.ts` for the OBD Service itself). If you add a new agent tool, add its name to `EXPECTED_TOOL_NAMES` in that test - a silent addition should fail the count check, not pass unnoticed.

`tests/diagnostics-engine.test.ts`, `tests/diagnostics-quality-benchmark.test.ts`, and `tests/diagnostics-fromLiveData.test.ts` cover `lib/diagnostics/` - every rule, the confidence-scoring cap/confirm/refute behavior, and the mission-specific quality-benchmark scenarios (lean mixture improving at higher RPM, trims elevated with no improvement, misfire without enough data, low voltage with the engine running, an incoherent sensor reading), plus a static scan proving no rule text ever contains a torque unit. `tests/agent-tools-diagnostics.test.ts` mocks `lib/obd-client` (via `vi.mock`) to test `capture_diagnostic_sample`/`run_diagnosis` behavior without a live OBD Service. When adding a new rule to `lib/diagnostics/rules.ts`, also add it to `ALL_RULES` and write a benchmark case for it here - a rule the engine never exercises is unverified reasoning, exactly what this project is set up to avoid.

Beyond content integrity, treat `lint`, `typecheck`, and a local smoke test in `npm run dev` as the minimum validation for app-code changes. For anything touching the Scanner, also start `obd-service` (simulator mode) and manually exercise `/scanner` end-to-end (connect, live data, disconnect, then check `/historico`) - the connect/disconnect/history flow has already broken once from a page being statically cached; a quick manual pass catches that class of bug faster than reasoning about it.

## Commit & Pull Request Guidelines
Git history is not available in this directory, so no local commit convention can be inferred. Use short, imperative commit messages such as `feat: add guide search filters` or `fix: handle empty systems list`. PRs should include a concise description, affected paths, validation commands, and screenshots for UI changes. Link the related issue when one exists.

## Security & Configuration Tips
Do not commit secrets from `.env`. Avoid editing generated output in `.next/` or dependencies in `node_modules/`. Database changes should include the Prisma schema update and matching migration files under `prisma/migrations/`.
